# AI 实时通话翻译工具需求文档

## 1. 项目概述

本项目旨在开发一款面向 macOS 和 Windows 的 AI 实时通话翻译工具。用户与外国人进行语音通话时，工具能够实时捕获双方语音，将对方语音识别、翻译并以本方语言展示或播报，同时将用户语音识别、翻译并通过语音合成输出为对方可理解的语言。

技术栈约束：

- Rust：核心音频采集、虚拟音频路由、实时调度、跨进程通信与性能关键路径。
- Python：ASR、机器翻译、TTS 等模型后端服务。
- Tauri：桌面端 UI、设置面板、状态展示和用户交互；Python 后端作为 sidecar 或外部本地服务由 Rust/Tauri 启停和连接，不应被视为 Tauri 原生能力。
- 平台：仅支持 macOS 与 Windows，暂不支持 Linux、移动端和 Web 端。

## 2. 产品目标

### 2.1 核心目标

- 在通话场景中提供低延迟、双向、可理解的语音翻译能力。
- 支持用户选择输入设备、输出设备和虚拟音频设备，适配常见通话软件。
- 在 UI 中清晰展示实时识别文本、翻译文本、当前语言方向、延迟、模型状态和音频路由状态。
- MVP 阶段优先采用本地 Python 模型服务实现 ASR、VAD、机器翻译和 TTS，先跑通本地端到端链路；在线 API 能力作为后续扩展方向预留。

### 2.2 MVP 目标

MVP 版本优先验证端到端链路：

1. 捕获本机麦克风语音。
2. 捕获对方通话音频或系统输出音频。
3. 对两路音频分别进行 ASR。
4. 根据语言方向进行翻译。
5. 将翻译结果进行 TTS 合成。
6. 将合成音频输出到指定设备或虚拟麦克风。
7. 在 UI 中展示实时字幕、链路状态和基础设置。

## 3. 目标用户与场景

### 3.1 目标用户

- 需要与外国客户、同事或朋友进行语音沟通的用户。
- 需要在远程会议、电话销售、客服、在线教育等场景中进行跨语言沟通的用户。
- 希望在本地设备上运行模型服务、减少音频和文本上传风险的用户。

### 3.2 典型场景

#### 场景 A：跨语言电话沟通

用户使用 Zoom、Teams、Discord、微信语音或其他通话软件与英语使用者沟通。工具监听双方语音：

- 对方英文语音被识别并翻译为中文。
- 用户中文语音被识别并翻译为英文。
- 英文 TTS 通过虚拟麦克风送入通话软件，让对方听到翻译后的语音。
- 中文翻译可通过字幕或本机扬声器播放给用户。

#### 场景 B：会议辅助字幕

用户只需要理解对方语言，不需要把自己的声音翻译给对方。工具仅捕获系统音频，实时展示本方语言字幕，也可以选择本方语言 TTS 播放。

#### 场景 C：客服或销售外呼

用户需要稳定的双向翻译、可配置术语表和固定话术。MVP 阶段只提供基础双向翻译，术语表与话术增强作为后续能力。

## 4. 范围定义

### 4.1 MVP 范围

- macOS 与 Windows 桌面应用。
- 麦克风音频采集。
- 系统输出音频或指定设备音频采集。
- 双向 ASR、翻译、TTS 链路。
- 多语言方向配置，用户可以在客户端自行选择本方语言与对方语言，不将 MVP 限制为固定语言对。
- 音频输入、输出和虚拟设备选择。
- 实时字幕面板。
- 链路状态监控：音量、识别中、翻译中、合成中、延迟、错误状态。
- 基础模型配置：模型路径、模型参数、设备类型、后端地址、启停控制。
- 基础日志与故障诊断信息。

### 4.2 非 MVP 范围

- 移动端应用。
- 浏览器插件。
- 视频翻译或唇形同步。
- 多人会议中的说话人分离与逐人翻译。
- 复杂术语库、记忆库、行业词典。
- 云端账号体系、计费系统和团队管理。
- 对所有通话软件做深度集成。
- 自研或随应用安装内核级虚拟音频驱动。
- 医疗、法律、金融等高风险场景的认证级翻译准确性保证。

### 4.3 MVP 前置假设

- 用户已具备或愿意安装第三方虚拟音频设备，用于把翻译后语音送入通话软件。
- MVP 只保证对通用系统音频设备链路可用，不保证每个通话软件的私有音频处理策略都兼容。
- 首批交付需要明确一组推荐模型组合和硬件基线，未覆盖语言或音色只展示为不可用，不应在 UI 中承诺可用。
- 本地模型首次下载、模型授权条款确认和离线缓存策略需要在安装或首次配置流程中明确展示。

## 5. 用户体验需求

### 5.1 主界面

主界面需要包含：

- 当前运行状态：未启动、启动中、运行中、暂停、错误。
- 双向语言方向：本方语言、对方语言。
- 音频链路状态：本方输入、对方输入、本方输出、虚拟麦克风输出。
- 实时字幕区域：原文、译文、时间戳、语音方向。
- 延迟指标：ASR 延迟、翻译延迟、TTS 延迟、端到端延迟。
- 快捷操作：开始、暂停、停止、静音本方翻译、静音对方翻译。

### 5.2 设置界面

设置界面需要包含：

- 麦克风输入设备选择。
- 对方音频捕获设备选择。
- 本机监听输出设备选择。
- 虚拟麦克风输出设备选择。
- 本方语言与对方语言选择。
- ASR、VAD、翻译、TTS 模型配置。
- 本地模型路径与运行设备配置。
- 在线模型服务配置作为后续扩展项预留。
- TTS 声音、语速、音量配置。
- 是否播放原声、是否播放译音、是否显示字幕。
- 日志级别与诊断信息导出。

### 5.3 状态反馈

- 当音频设备不可用时，UI 应明确提示设备名称和错误类型。
- 当 Python 模型后端未启动或不可连接时，UI 应提示用户启动或重新连接。
- 当模型处理延迟过高时，UI 应显示警告，但不中断通话链路。
- 当虚拟音频设备未配置时，UI 应提供配置说明或引导。

### 5.4 关键用户流程

首次启动流程：

1. 用户选择本方语言和对方语言。
2. 应用检查 ASR、翻译和 TTS 是否都支持所选语言链路。
3. 用户选择麦克风、对方音频捕获设备、本机监听输出设备和虚拟麦克风输出设备。
4. 应用检查麦克风权限、系统音频捕获能力、虚拟设备配置和 Python 后端健康状态。
5. 用户确认是否保存录音、转写文本和翻译文本。
6. 应用进入可启动状态。

会话中流程：

- 用户可以查看两路字幕、延迟、模型状态和音频电平。
- 用户可以暂停、恢复、停止会话，或单独静音某一方向的 TTS。
- 当延迟过高、队列积压、设备断开或后端不可用时，UI 应展示可操作的恢复建议。

会话结束流程：

- 应用释放音频设备和模型任务。
- 应用根据用户配置保存或丢弃录音、转写文本和翻译文本。
- 用户可以在历史界面查看或删除已保存会话。

## 6. 功能需求

### 6.1 音频采集

Rust 核心层负责采集音频：

- 支持麦克风输入采集。
- 支持系统输出音频或指定设备音频采集；应用级音频捕获作为平台能力允许时的增强项，不作为 MVP 硬性承诺。
- 支持 macOS 和 Windows 的平台差异封装。
- 支持音频帧切分、重采样、声道转换和音量归一化。
- 支持 VAD，用于降低无语音片段的模型调用成本。
- 支持回声和串音控制策略，避免 TTS 输出再次进入 ASR 链路。

MVP 阶段首选 `silero-vad` 作为 VAD 模型。音频输入需要在进入 VAD 前统一到模型支持的采样率，优先使用 16 kHz 单声道 PCM；设备采集和播放可保留 48 kHz，但必须在 Rust 层或 Python 层完成明确的重采样边界。

### 6.2 ASR 语音识别

Python 模型后端负责 ASR：

- 接收 Rust 层传入的音频帧或语音片段。
- 返回增量识别结果和最终识别结果。
- 支持本方语音与对方语音两条独立流。
- 支持语言自动检测或固定语言模式。
- MVP 阶段首选 `faster-whisper` 提供多语言识别能力，用户可在客户端选择识别语言；具体支持语种取决于模型能力。
- 支持结果置信度、起止时间戳和分段 ID。
- MVP 实时识别采用短音频片段滚动推理策略，不将 `faster-whisper` 本身视为完整流式 ASR 引擎；需要定义临时结果刷新、最终结果确认和重复文本去重规则。
- 需要支持 ASR 模型尺寸、量化方式、运行设备和线程数配置，并在 UI 中展示当前配置对延迟和资源占用的影响提示。

### 6.3 机器翻译

Python 模型后端负责翻译：

- 根据语音方向选择源语言和目标语言。
- MVP 阶段首选 `NLLB` 支持用户在客户端选择源语言与目标语言，不限制为固定语言对；具体支持语种取决于模型能力。
- 支持短句实时翻译。
- 支持上下文窗口，以改善连续对话翻译质量。
- 返回翻译文本、分段 ID 和处理耗时。
- 保留术语表扩展接口，但 MVP 不实现复杂术语管理。
- 需要维护 UI 语言名称、ASR 语言码、NLLB/FLORES 语言码和 TTS voice 语言码之间的映射表；当任一阶段不支持所选语言时，UI 应阻止启动并提示缺失阶段。
- NLLB 输入应按短句或语义分段处理，避免长上下文超过模型适用长度导致质量下降；上下文窗口只作为翻译提示，不应无限累积。

### 6.4 TTS 语音合成

Python 模型后端负责 TTS：

- 将翻译文本合成为目标语言音频。
- MVP 阶段首选 `Piper TTS` 提供语音合成能力，具体支持语种和音色取决于模型能力。
- 支持配置声音、语速、音量和采样率。
- 支持流式或分段输出音频。
- 返回音频数据、分段 ID、音频时长和处理耗时。
- 每个 Piper voice 至少需要模型文件和配置文件，应用需要校验 voice 文件完整性、语言匹配和授权信息。
- 当目标语言没有可用 TTS voice 时，应用应允许字幕模式继续运行，并明确提示该方向无法播放译音。
- MVP 应优先采用常驻 TTS 进程或服务复用已加载 voice，避免每个分段重新启动 CLI 和加载模型；如使用 Piper 原始音频流输出，需要明确 PCM 格式、采样率和播放缓冲策略。

### 6.5 音频输出与路由

Rust 核心层负责输出音频：

- 将对方语音翻译后的本方语言 TTS 输出到本机监听设备。
- 将本方语音翻译后的目标语言 TTS 输出到虚拟麦克风或指定输出设备。
- 支持单独开启或关闭任一方向的 TTS 输出。
- 支持字幕优先模式，即只展示译文，不播放 TTS。
- 支持输出队列调度，避免多个 TTS 片段重叠播放。
- 支持基础播放策略：顺序播放、丢弃过期片段、按方向静音和清空队列。
- 双向同时说话时，MVP 允许语音播放自然度下降，但必须避免同一输出设备上多段 TTS 互相叠加。

### 6.6 实时字幕

Tauri UI 负责展示字幕：

- 显示本方原文、本方译文、对方原文、对方译文。
- 支持按时间顺序滚动。
- 支持区分识别中的临时文本与最终文本。
- 支持复制当前字幕内容。
- 支持清空当前会话字幕。

### 6.7 录音、转写与翻译历史

应用需要支持会话历史能力：

- 支持保存通话录音。
- 支持保存 ASR 转写文本。
- 支持保存翻译文本。
- 支持按会话查看历史记录。
- 支持用户手动删除历史记录。
- 历史保存需要提供显式开关，默认策略应在 UI 中明确展示。
- MVP 默认不保存录音、转写文本和翻译文本；首次启动可引导用户主动开启文本历史保存，不允许在未提示情况下静默保存敏感内容。
- 历史记录需要至少包含会话时间、语言方向、分段文本和保存类型；录音文件应与文本历史建立可追踪关联。
- 删除会话历史时，应同时删除该会话关联的录音、转写文本、翻译文本和索引记录。

### 6.8 会话控制

- 用户可以启动、暂停、恢复和停止翻译会话。
- 停止会话后需要释放音频设备和模型任务。
- 暂停会话时需要保留配置，但停止音频采集和模型推理。
- 异常恢复后应允许用户重新启动会话。
- 开始会话前需要完成配置预检，包括音频设备可用性、虚拟设备配置、模型文件存在性、语言链路支持和 Python 后端健康状态。

### 6.9 模型资产管理

- 支持配置本地模型目录和缓存目录。
- 支持展示每个模型或 voice 的名称、版本、大小、语言覆盖、运行设备和加载状态。
- 支持模型文件完整性检查，至少覆盖文件是否存在、配置是否匹配和加载是否成功。
- 支持模型热身，以减少首次 ASR、翻译或 TTS 请求延迟。
- 首批推荐模型组合需要在发布说明中列明，包括 ASR 模型尺寸、NLLB 模型版本、Piper voice 列表和最低硬件建议。

### 6.10 实时分段与调度

- 音频分段需要同时考虑 VAD 结束点、最大分段时长和最大静音等待时间。
- 每个分段在 ASR、翻译、TTS 三阶段需要保持同一 `segment_id`，并记录阶段耗时。
- 当队列积压导致端到端延迟超过阈值时，系统应优先丢弃或跳过过期的 TTS 播放片段，而不是阻塞新的识别和字幕展示。
- 临时字幕可被更新或覆盖，最终字幕一旦确认不应被后续模型结果静默改写。
- ASR 需要支持滚动缓冲、稳定文本提交和最终 flush，避免实时识别中重复提交同一段文本。
- TTS 需要支持取消或打断尚未播放的过期片段，停止会话时必须清空待播放缓冲。

## 7. 非功能需求

### 7.1 延迟

目标延迟按端到端链路衡量：

- MVP 可接受目标：单向端到端延迟小于 3 秒。
- 优化目标：单向端到端延迟小于 1.5 秒。
- UI 应展示当前链路耗时，便于定位瓶颈。
- 验收时需要明确测试硬件、模型组合、语言方向、采样率和网络状态；默认按本地模型、推荐模型组合和无云端调用评估。
- 延迟指标需要区分字幕端到端延迟和 TTS 播放端到端延迟，避免只优化字幕而忽略语音输出。

### 7.2 稳定性

- 会话运行期间不应因单个模型请求失败导致整个应用崩溃。
- 音频设备断开后应展示错误，并允许重新选择设备。
- Python 后端异常退出时，Rust 层和 UI 应进入可恢复状态。

### 7.3 隐私与安全

- MVP 阶段默认使用本地模型服务处理音频、识别文本和翻译文本，不默认上传到云端。
- 若后续启用在线模型服务，UI 必须明确展示当前使用在线服务，并提示用户相关音频与文本数据会发送到对应服务。
- 本地日志默认不记录完整音频内容。
- 诊断日志如包含文本内容，需要提供开关。
- 录音、转写和翻译历史默认保存策略必须可配置，用户应能关闭历史保存并删除已有历史。
- 应用需要提示用户遵守通话录音和转写相关法律法规；涉及录音保存时必须由用户主动开启。
- 在线 Provider 预留能力不得在 MVP 中默认启用，也不得在未获得用户确认时回退到在线服务。

### 7.4 性能

- Rust 层需保证音频采集与输出线程不被模型推理阻塞。
- Python 后端需支持异步处理或队列处理，避免单个任务阻塞全部链路。
- UI 更新频率需要受控，避免字幕高频刷新导致界面卡顿。

### 7.5 可维护性

- Rust 核心层、Python 模型层、Tauri UI 层之间通过明确协议通信。
- 音频帧、ASR 结果、翻译结果、TTS 音频结果需要统一分段 ID。
- 每个模块应具备独立启动、停止和错误上报能力。

### 7.6 可测试性

- Rust 音频核心层需要支持使用本地 WAV 文件或模拟音频源进行链路测试。
- Python 模型后端需要支持健康检查、模型加载检查和单阶段推理测试接口。
- 端到端测试需要覆盖至少一个本方到对方方向和一个对方到本方方向。
- 平台兼容验证需要分别记录 macOS 和 Windows 的音频设备枚举、采集、播放和虚拟设备路由结果。

## 8. 技术架构需求

### 8.1 总体架构

```text
通话软件/系统音频
      |
      v
Rust 音频核心层  <---->  Tauri UI
      |
      v
Python 模型后端
      |
      v
ASR -> 翻译 -> TTS
      |
      v
Rust 音频输出/虚拟设备路由
```

### 8.2 Rust 核心层职责

- 管理音频输入输出设备。
- 处理实时音频帧、缓冲区和队列。
- 进行重采样、声道转换、VAD 和基础音频增强。
- 调度 ASR、翻译、TTS 请求。
- 与 Python 后端通信。
- 向 Tauri UI 推送状态、字幕和错误事件。
- 管理虚拟音频设备输出。

### 8.3 Python 模型后端职责

- 提供 ASR、翻译、TTS 服务接口。
- 管理模型加载、卸载和热身。
- MVP 阶段支持本地 ASR、VAD、翻译、TTS 模型加载与调用。
- 首选 ASR 模型为 `faster-whisper`。
- 首选 VAD 模型为 `silero-vad`。
- 首选翻译模型为 `NLLB`。
- 首选 TTS 模型为 `Piper TTS`。
- 预留在线模型服务 Provider 接口，但不作为 MVP 首要实现目标。
- 支持流式或分段式推理。
- 返回结构化结果和耗时指标。
- 暴露健康检查接口。

### 8.4 Tauri UI 职责

- 提供主界面、设置界面和诊断界面。
- 调用 Rust 命令启动、暂停、停止会话。
- 订阅 Rust 层事件，展示实时状态。
- 保存和加载用户配置。
- 展示设备、模型、语言和链路错误。

### 8.5 层间通信

推荐通信方式：

- Tauri UI 与 Rust：使用 Tauri command 和 event。
- Rust 与 Python：MVP 优先采用本地 WebSocket 承载控制消息和二进制音频帧；gRPC、Unix Domain Socket 和 Windows Named Pipe 作为后续优化或替代方案预留。
- 音频数据传输：采用二进制帧，避免频繁 Base64 编解码。
- 状态与控制消息：MVP 采用 JSON；MessagePack 作为性能优化预留。

基础消息字段：

```text
protocol_version: 协议版本
session_id: 会话 ID
stream_id: audio_local 或 audio_remote
segment_id: 语音分段 ID
direction: local_to_remote 或 remote_to_local
source_lang: 源语言
target_lang: 目标语言
timestamp_ms: 时间戳
sequence_no: 同一流内递增序号
is_final: 是否为最终结果
payload: 音频或文本负载
latency_ms: 处理耗时
error_code: 错误码，可为空
```

协议设计要求：

- 控制面消息用于会话启停、配置、状态和错误；数据面消息用于音频帧、ASR、翻译和 TTS 结果。
- 协议版本需要随每次连接和健康检查返回，版本不兼容时 UI 应提示升级或重启对应组件。
- 大音频负载不得进入 JSON 文本字段，应使用 WebSocket binary frame 或等价二进制通道传输。

MVP 需要定义以下消息类型：

```text
session.start: 启动会话
session.pause: 暂停会话
session.stop: 停止会话
audio.frame: 音频帧
asr.partial: ASR 临时结果
asr.final: ASR 最终结果
translate.result: 翻译结果
tts.audio: TTS 音频结果
status.update: 状态更新
error: 错误事件
```

### 8.7 Python Model Service 内部分层

Python Model Service 推荐按以下模块拆分：

```text
Python Model Service
  ├── API Layer
  │   ├── FastAPI
  │   ├── WebSocket
  │   └── Health Check
  │
  ├── Session Manager
  │   ├── session_id
  │   ├── source_lang
  │   ├── target_lang
  │   └── current_pipeline_state
  │
  ├── ASR Engine
  │   ├── faster-whisper
  │   ├── model cache
  │   └── language detection
  │
  ├── VAD Engine
  │   └── silero-vad
  │
  ├── Translation Engine
  │   ├── NLLB
  │   ├── OPUS-MT
  │   └── Argos
  │
  ├── TTS Engine
  │   ├── Piper
  │   ├── MeloTTS
  │   └── system TTS
  │
  ├── Pipeline Orchestrator
  │   ├── asr_queue
  │   ├── translate_queue
  │   ├── tts_queue
  │   └── result_queue
  │
  └── Runtime
      ├── GPU/CPU device manager
      ├── model loader
      ├── model unloading
      └── logs/metrics
```

分层职责要求：

- API Layer 负责接收 Rust 核心层请求，提供 FastAPI、WebSocket 和健康检查接口。
- Session Manager 负责维护会话 ID、语言方向和当前流水线状态。
- ASR Engine 首选 `faster-whisper`，并支持模型缓存和语言检测。
- VAD Engine 首选 `silero-vad`，用于过滤静音片段并降低 ASR 调用压力。
- Translation Engine 首选 `NLLB`，同时预留 `OPUS-MT` 和 `Argos` Provider。
- TTS Engine 首选 `Piper TTS`，同时预留 `MeloTTS` 和系统 TTS Provider。
- Pipeline Orchestrator 负责维护 ASR、翻译、TTS 和结果队列，保证实时链路不会被单个阶段阻塞。
- Runtime 负责 GPU/CPU 设备选择、模型加载、模型卸载、缓存、日志和指标。

## 9. 平台要求

## 10. 配置需求

应用需要持久化以下配置：

- 本方语言。
- 对方语言。
- 麦克风输入设备 ID。
- 对方音频捕获设备 ID。
- 本机监听输出设备 ID。
- 虚拟麦克风输出设备 ID。
- ASR 模型配置，默认 `faster-whisper`。
- VAD 模型配置，默认 `silero-vad`。
- 翻译模型配置，默认 `NLLB`。
- TTS 模型配置，默认 `Piper TTS`。
- 模型路径、缓存目录和运行设备配置。
- TTS 声音、语速、音量。
- 是否启用本方到对方翻译。
- 是否启用对方到本方翻译。
- 是否显示字幕。
- 是否播放 TTS。
- 是否保存录音。
- 是否保存转写文本。
- 是否保存翻译文本。
- 历史保存目录。
- Python 后端地址、端口和自动启动策略。
- VAD 阈值、最小语音时长、最大分段时长和静音结束时长。
- ASR 计算精度、beam size、线程数和是否启用语言自动检测。
- 翻译上下文窗口大小和最大输入长度。
- TTS 输出采样率、目标输出设备和队列过期阈值。

默认配置要求：

- 录音保存默认关闭。
- 转写文本和翻译文本保存默认关闭，首次启动时可引导用户主动开启。
- 在线模型服务默认关闭。
- 字幕显示默认开启。
- 双向 TTS 默认需要用户完成设备预检后才能开启。

## 11. 错误与诊断需求

### 11.1 错误类型

- 音频设备不可用。
- 麦克风权限未授权。
- 系统音频捕获失败。
- 虚拟音频设备未配置。
- Python 后端不可连接。
- 模型文件不存在或路径无效。
- 模型加载失败。
- GPU/CPU 运行设备不可用。
- ASR 请求失败。
- 翻译请求失败。
- TTS 请求失败。
- 输出队列阻塞或延迟过高。
- 语言链路不完整，例如 ASR 支持但 TTS voice 缺失。
- 模型授权或下载状态未确认。
- 音频采样率转换失败。
- WebSocket 连接中断或协议版本不兼容。

### 11.2 诊断信息

诊断界面应展示：

- 当前应用版本。
- 操作系统版本。
- 可用音频设备列表。
- Python 后端连接状态。
- 模型加载状态。
- 当前模型来源：本地 Python 模型服务。
- GPU/CPU 设备状态。
- 最近错误日志。
- 最近一次端到端链路耗时。
- 当前协议版本。
- 当前音频采样率、声道数和重采样状态。
- 当前队列长度和各阶段平均耗时。

## 12. 验收标准

MVP 版本满足以下条件视为通过：

- 用户可以在 macOS 或 Windows 上启动桌面应用。
- 用户可以选择麦克风、对方音频输入和输出设备。
- 用户可以在客户端选择本方语言与对方语言。
- 用户可以配置本地 ASR、VAD、翻译、TTS 模型。
- 应用可以捕获本方语音并展示 ASR 文本。
- 应用可以捕获对方语音并展示 ASR 文本。
- 应用可以将本方语音翻译为对方语言文本。
- 应用可以将对方语音翻译为本方语言文本。
- 应用可以将翻译文本合成为语音并输出到指定设备。
- 应用可以展示实时字幕和链路状态。
- 应用可以根据用户配置保存录音、转写文本和翻译文本历史。
- 在推荐硬件和推荐模型组合下，使用首批验收语言对和标准测试音频，单向字幕端到端延迟 P95 低于 3 秒。
- 在推荐硬件和推荐模型组合下，单向 TTS 播放端到端延迟达到可用水平，并在超过阈值时显示延迟警告。
- Python 后端异常退出时，UI 能显示错误且应用不崩溃。
- 停止会话后音频设备被释放。
- 选择不完整语言链路时，应用能在启动前提示缺失的 ASR、翻译或 TTS 能力。
- 关闭历史保存后，新会话不应保存录音、转写文本或翻译文本。
- macOS 和 Windows 均完成至少一次麦克风采集、系统或设备音频捕获、本机播放和虚拟设备输出验证。
- 应用连续运行 30 分钟不崩溃；停止会话后，麦克风和输出设备可被其他应用重新打开。
- Python 后端断开后，UI 在 5 秒内显示错误，并允许用户重新连接或停止会话。

## 14. 风险与待确认问题

### 14.1 主要风险

- 系统音频捕获和虚拟音频路由在 macOS 与 Windows 上差异较大。
- 本地 ASR、翻译、TTS 模型可能造成较高延迟、内存占用或 GPU/CPU 资源占用。
- 不同语言方向的模型质量、TTS 音色覆盖和端到端延迟可能不一致。
- TTS 输出可能被本方 ASR 再次捕获，导致翻译回环。
- 双向同时说话时，分段、队列和播放策略会影响自然度。
- 通话软件的音频设备配置对普通用户可能较复杂。
- NLLB 与部分 Piper voice 的授权、用途限制或语言覆盖可能影响模型分发方式。
- `faster-whisper`、`NLLB` 和 `Piper TTS` 的本地组合可能难以在低配 CPU 设备上同时满足 3 秒延迟目标。
- macOS 系统音频捕获依赖系统版本、权限和第三方虚拟设备，用户配置成本较高。

### 14.2 已确认产品决策

- 语言方向不限制为 `中文 <-> 英文`，用户可以在客户端选择本方语言与对方语言；实际可用语种由模型能力决定。
- MVP 阶段首选本地模型服务：ASR 使用 `faster-whisper`，VAD 使用 `silero-vad`，翻译使用 `NLLB`，TTS 使用 `Piper TTS`。
- MVP 阶段不内置虚拟音频驱动，仅提供第三方虚拟音频设备配置说明。
- 需要支持录音、转写和翻译历史保存能力。
- 不针对特定通话软件做专用对接，目标是通过系统音频与虚拟音频设备让电脑上的通话软件通用可用。

### 14.3 待确认问题

- MVP 首批内置或推荐下载哪些具体模型尺寸、语言包和 TTS 音色。
- MVP 首批验收语言对有哪些，是否只对这些语言对承诺延迟和质量目标。
- MVP 推荐硬件基线是什么，例如 CPU、内存、GPU、显存和 Apple Silicon 型号。
- 是否允许应用提供模型下载器，还是只允许用户手动配置本地模型路径。
- 历史记录是否需要支持自动清理周期，例如保留 7 天、30 天或永久保留。
- 是否需要为首批语言对设定质量验收样例和人工评分标准。
- WebSocket 协议是否需要从第一版开始固定版本号和兼容策略。
